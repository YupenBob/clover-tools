Unexpected token '<'：JSON 接口为什么返回了 HTML？

用一个实际返回 HTML 的接口复现 JSON 解析失败，按状态码、Content-Type、重定向和响应正文定位登录页、路径错误与代理错误。

立即打开 JSON 格式化与校验

Unexpected token '<' 出现在 JSON.parse() 或 response.json() 附近，最常见的情况是：代码期待 JSON，实际读到的内容却以 <!doctype html> 或 <html> 开头。这里该追查的是响应从哪里来，而不是把尖括号删掉。

错误措辞会随浏览器版本改变，有时还会显示 “is not valid JSON”。先看响应正文才能下结论：字符 < 是线索，并不能单独证明返回的一定是登录页。

200 也可能是一张登录页面

想在自己的电脑上核对？下载本地 HTTP 复现脚本，安装 Node.js 后运行 node http-repro.mjs，再打开 http://127.0.0.1:8765。脚本只监听本机的 8765、8766 两个端口，无须密钥；用完在终端按 Ctrl+C 关闭。

在本地样例里点击“把 HTML 当作 JSON 读取”。/api/profile 返回状态 200、类型 text/html，正文是一段演示登录页。页面把同一份文本交给 JSON.parse()，就会看到下面的错误。

这个例子提醒我们，response.ok 只能检查 2xx 状态，不能保证正文符合接口契约。页面和 API 可能共用一个站点，错误路由恰好返回了前端首页，或者认证系统跳转到登录页面，最终都可能得到 200。

在 Network 里记下四样东西

  1. 实际 URL。 核对域名、路径和查询参数；有重定向时，检查跳转链以及最终地址。fetch 默认会跟随重定向。
  2. 状态码。 404 优先查路由，401/403 查身份与权限，502/503 查上游；200 则继续看类型与正文。
  3. Content-Type。 text/html 与 application/json 明显不同；有些 API 使用以 +json 结尾的媒体类型。
  4. 原始正文的开头。 是你的网站首页、登录表单，还是代理服务生成的错误页？不要只看经过前端包装后的“解析失败”。
响应长什么样常见原因修复落点
你自己网站的完整首页API 路径未命中，被 SPA 回退规则接管让 /api 路由在页面回退之前匹配，并核对生产环境 API 基址。
登录页面或认证提示会话失效、Cookie 未携带、认证重定向按服务的认证流程修复；API 最好用明确的 401/403 和约定的错误格式。
带网关或服务商标记的错误页上游失败、超时或访问规则触发根据状态和请求 ID 查网关/源站日志，不要用 JSON 格式化器“修复”HTML。
正文为空204 No Content，或服务端没有返回正文按接口约定处理空响应；直接解析空字符串通常会得到另一类语法错误。

给读取代码留一个能看懂的出口

与其把所有错误都交给 response.json()，可以先检查状态和媒体类型。下面这段适合约定必须返回 JSON 的接口；如果你的接口合法返回 204，应在业务层单独处理。

async function readJson(response) {
  const type = (response.headers.get('content-type') || '')
    .split(';')[0].trim().toLowerCase();
  const text = await response.text();

  if (!response.ok) {
    throw new Error('HTTP ' + response.status);
  }
  if (type !== 'application/json' && !type.endsWith('+json')) {
    throw new Error('Expected JSON, received ' + (type || 'unknown type'));
  }
  return JSON.parse(text);
}

const response = await fetch('/api/profile');
const data = await readJson(response);

响应体通常只能消费一次。上面的代码先 text()，再解析保存下来的文本；不要紧接着又对同一个 Response 调用 json()。若确实需要两份独立读取，应在第一次读取前使用 response.clone()，并考虑大响应的内存成本。

媒体类型检查能给出清楚的提示，但它也不是语法校验。服务器即使写了 JSON 响应头，正文仍可能损坏，所以最后的解析错误仍需保留。

格式化器应该放在排查的哪一步

确认拿到的确实是 JSON 文本之后，再用JSON 格式化器检查引号、逗号和嵌套层级。它能验证已有文本，不能修复错误的接口地址，也不能替过期会话重新登录。

如果 Network 根本读不到响应，而 Console 提示 CORS，则回到Failed to fetch 的排查。先拿到正确响应，再讨论 JSON 的格式，通常能少走一圈。
