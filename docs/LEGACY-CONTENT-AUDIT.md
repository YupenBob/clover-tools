**内容质量与流量质量分别判断。** 你提到“流量大但并不高质”，应重点看文章访问是否带来目标用户、实际工具使用与回访。不能用模板比例直接推断来访者质量。你的运营经验是旧文章曾带来大量流量；这一点应保留为重要背景。Git 能证明它具备覆盖大量长尾搜索的结构，但不能证明访问规模、搜索来源或转化率。代码中能直接确认的内容问题包括：

- 通用 `error-fix` 模板把很多问题归到 JSON 格式、编码和参数类型；例如“ai生成失败怎么办”被推荐到正则测试器，无法系统回答其账户、模型或服务故障问题。824 条配置中，87 条指向同一个正则工具；这不证明 87 条都错误，却值得逐条审查关联性。
- `encoding` 模板把 Base64 普遍要求成带 Data URL 前缀，适用范围不准确；`guide` 的通用 FAQ 还把编码工具描述成适合“加密传输”。这些是技术概念问题。
- 即使正文是专门写的，生成器仍统一附上按意图套用的 FAQ；有独立正文不代表整个页面都准确。
- 文章显示日期和博客 sitemap 的 `lastmod` 都按构建当天生成，不能反映真实内容更新。
- 登记表有 137 条文章，但查找使用 `articlesConfig[kw.keyword]`，登记时却以 `a.slug` 为键；叠加文件名规则差异，会让部分准备好的正文未被选用。
- 824 条关键词里，151 条没有工具目标，另有 3 条目标不在当时工具登记表内。是否能引导用户完成任务，需要看正文和实际功能，不能用“有 CTA”替代检查。

**重构中损失的是什么。** 新构建没有接入 `data/articles.json`、`data/keywords.json` 或归档正文；这些文件留在 Git 里，不会自动变成网站页面。旧博客、6 个问题聚合页及其内链网络也没有被现有 16 篇指南一对一接替。源码层面被切断的是“具体问题 → 文章回答 → 相关工具”的路径。

现行 `public/_redirects` 和 `scripts/gen-redirects.mjs` 将 `/blog/*`、`/fix/*` 全部配置为 301 到首页。对于搜索某个具体报错的用户，首页不等于原问题的答案。Google 的[站点迁移文档](https://developers.google.com/search/docs/crawling-indexing/site-move-with-url-changes)建议建立对应网址映射，并明确指出，大量旧页跳到不相关首页可能被视为 soft 404。这里能确认的是**迁移配置风险**，不能据此宣称本网站已被 Google 判为 soft 404、确定损失多少排名，或认定它就是 AdSense 拒绝的原因。

**建议的下一步。** 先做一批可审查的旧内容迁移，规模服从需求与校对能力。按以下顺序处理：

1. 把附件中的旧网址与历史搜索、访问和外链记录合并。优先核对 8 月 2 日前后的等长时段，单独分析 10 月 11 日；如数据不覆盖历史时段，则记录缺失，不补造曲线。同时区分旧域名 `tools.xsanye.cn` 与 `clovertools.cn`，避免把域名变化和重构影响混在一起。
2. 先审查与现有工具强相关的问题：JSON 解析、正则边界、时间戳单位、Base64、JWT 解码。附件中可追溯的候选包括 `/blog/jsonparse报错终结方案`、`/blog/正则永远匹配不到这篇帮你彻底搞懂`、`/blog/时间戳10位13位踩坑完全手册` 和 `/blog/jwttoken过期怎么查看`。这些是内容相关性候选，尚未证明是流量最高的页面。
3. 对保留的问题重写正文：直接回答标题问题，提供错误输入、修复步骤、实际结果、环境差异和适用限制；工具入口只在确实能完成这一步时推荐。旧“翻车经历”、测试数字和成功率需要来源，不能原样作为可信证据。
4. 给每个旧网址指定处置：原网址重写并返回 200；确实同题合并则精确 301 到对应内容；没有价值且无对应内容则返回真实 404/410。处理无后缀、`.html`、大小写和中文编码的历史别名，统一到一个 canonical。
5. 内容与逐页映射准备好后，再同步修改生成重定向的脚本及输出文件，替换相关的首页兜底规则，并检查跳转链。不要先拆掉规则，再让旧入口悬空。
6. 用轻量、明确的导航接回保留文章；更新 sitemap、文章与工具往返链接。每篇使用真实更新日期，逐页检查手机阅读和操作体验，再验证发布结果。
7. 将搜索点击、文章到工具的点击、实际任务完成分开衡量。现有 Web Analytics 数据不自动包含任务完成事件；需要时再设计最小统计与披露。以使用结果决定扩写、合并或停更。
